# Universal Rail: Staff Role Complete Item Catalog

> Date: 2026-05-14
> Role: `staff` (team member inside a chef tenant: sous chef, prep cook, server, bartender, dishwasher, support)
> Scope: Every item type that can appear on the Universal Rail for STAFF users.
> Core promise: Clock in, look at the rail, know exactly what the day looks like.

The staff Universal Rail is the operational work surface. It must be fast, scoped, and low-noise. Staff see only what is assigned to them, shared with them, needed for their station, or needed for today's shift. They do not see chef financials, client personal data, pricing strategy, margin, revenue, business health, or private client notes unless the chef explicitly shares a safe operational excerpt.

Existing staff surfaces:

| Route              | Role in rail                                      |
| ------------------ | ------------------------------------------------- |
| `/staff-dashboard` | Default briefing, cross-category overview         |
| `/staff-recipes`   | Assigned recipes, prep methods, yields, allergens |
| `/staff-schedule`  | Shifts, swaps, availability, coverage             |
| `/staff-station`   | Station assignment, station checklist, handoff    |
| `/staff-tasks`     | Delegated tasks and dependencies                  |
| `/staff-time`      | Clock state, hours, timesheet reminders           |

## Legend

| Field               | Meaning                                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `baseUrgency`       | 0-100 static priority before time, route, behavior, and suppression signals                                                           |
| `urgencyDecayFn`    | `deadline` increases toward due time and expires after; `linear` fades over a window; `none` remains stable until explicitly resolved |
| `pageAffinity`      | Staff routes that boost the item                                                                                                      |
| `pageAffinityBoost` | 0-50 score added while on an affinity route                                                                                           |
| `presentation`      | `pill`, `card`, `badge`, `alert`, `progress`, `story`                                                                                 |
| `hoverAction`       | Desktop hover preview behavior                                                                                                        |
| `clickAction`       | `navigate`, `toggle_filter`, `expand_inline`, `quick_action`                                                                          |
| `maxImpressions`    | Times shown before suppressing without new signal. `-1` means never suppress while active                                             |
| `privacy`           | Staff-visible tenant data only. Default is assigned/shared operational data                                                           |

## Global Staff Rail Rules

1. Never show chef revenue, margin, pricing, payment state, payroll totals, or business metrics.
2. Never show client phone, email, address, payment data, private preferences, household data, or free-form client notes.
3. Guest dietary alerts may show only operationally necessary labels such as `Guest 3: severe nut allergy`. Use guest names only when the chef explicitly shared them to staff for service.
4. Every item must be scoped by `staff_member_id`, `chef_id`/`tenant_id`, assigned station, assigned event, or an explicitly shared team announcement.
5. Chef messages and task notes should render as operational excerpts. Do not expose full client communication threads.
6. Default ordering is: safety/allergy, active shift/time, overdue work, imminent work, station, event context, messages, onboarding/personal.

## Detailed Category Notes

### Shift and Schedule

Schedule items are the rail's daily skeleton. They should answer: am I working, when do I start, where do I go, and did anything change?

- `staff.todays_shift` is the default shift anchor for the day. It should remain visible while the staff member has an active shift, but it should not sit above safety alerts, overdue tasks, or clock reminders.
- `staff.upcoming_shifts_week` is a light planning card. It should collapse into one item even if the staff member has many shifts.
- `staff.schedule_change_alert` must require acknowledgment for same-day or next-day changes.
- `staff.shift_swap_request` and `staff.shift_coverage_request` are actionable only when the staff member is eligible. Ineligible staff should not see them.
- `staff.overtime_warning` must never expose wages, hourly rate, labor cost, or payroll math. It is strictly hours-based.
- `staff.no_shifts_next_week` is low urgency and should suppress quickly. It is informational, not disciplinary.
- `staff.availability_conflict` should beat normal schedule cards because it creates operational risk.

### Tasks and Delegation

Task items are the rail's action engine. The rail must avoid showing ten separate task cards when a grouped list is more useful.

- `staff.new_task_assigned` appears when the assignment is new or materially changed.
- `staff.task_due_soon` takes over when the staff member has seen the task and the due window is close.
- `staff.task_overdue` is the primary escalation state and should suppress other cards for the same task.
- `staff.task_completed_confirmation` is intentionally brief and low urgency.
- `staff.task_reassigned` should remove the task from active work surfaces immediately after it is no longer assigned.
- `staff.bulk_task_list` should be generated when three or more active tasks share the same event, date, or station.
- `staff.task_dependency` must show only enough information to explain the block. If the blocker belongs to another staff member, expose status, not private notes.
- `staff.task_notes_from_chef` should be pinned above the underlying task only when the note is new since the staff member last opened the task.

### Station Assignments

Station items make the rail feel like a kitchen clipboard. They should be concise and ready for gloved, quick scanning.

- `staff.current_station` is the station parent card for the current shift/event.
- `staff.station_change` is an alert until acknowledged. It should update task and recipe grouping immediately.
- `staff.station_prep_checklist` owns station readiness progress.
- `staff.station_equipment_check` should route equipment issues back to the chef/station lead without exposing broader operations.
- `staff.station_handoff` is time-sensitive and should surface before and during the handoff window.

### Event Context

Staff event context is a filtered brief, not the full event record.

- `staff.today_event_summary` should include event type, guest count, menu theme, timing, station, and assigned role. It must not include client contact data, payment data, address details, or private client notes unless explicitly shared as an operational location/instruction.
- `staff.event_timeline` shows milestones relevant to the staff member.
- `staff.event_dietary_alerts` is safety-critical and should outrank all non-clock safety items.
- `staff.event_menu` highlights staff-owned dishes rather than the full business menu management view.
- `staff.event_special_instructions` should carry only chef-shared operational instructions.
- `staff.upcoming_event_preview` is a planning card and should convert to today's summary on event day.
- `staff.post_event_cleanup` appears after service milestones and can remain through reset.

### Recipes

Recipe cards are for assigned prep and service work, not recipe costing or business intelligence.

- `staff.recipe_to_prep` links the task and recipe together.
- `staff.recipe_update` requires acknowledgment when the recipe is assigned today.
- `staff.recipe_technique_reminder` should be used sparingly and mostly for new staff, difficult techniques, or chef-required refreshers.
- `staff.recipe_yield_needed` must show scaled operational quantities, never cost.
- `staff.recipe_allergen_flag` is safety-critical and should be linked to dietary alerts when event-specific.

### Communication

Communication items are operational messages, not inbox replacement.

- `staff.message_from_chef` can outrank most non-safety work if unread and recent.
- `staff.message_from_staff` is scoped to same event/station/task or explicitly shared team threads.
- `staff.team_announcement` is a low-to-medium card unless acknowledgment is required.
- `staff.chef_feedback` should feel lightweight and disappear quickly.

### Inventory and Supplies

Inventory visibility is need-to-know.

- `staff.low_stock_alert` shows item, quantity, station/task impact, and instruction. It must not show cost, vendor contract terms, or margin.
- `staff.delivery_arriving` shows receiving instructions and storage notes, not invoices.
- `staff.inventory_count_due` exposes only count fields needed to perform the assigned count.
- `staff.item_substitution` must propagate to recipes, tasks, labels, and allergen warnings.

### Time Tracking

Time tracking items are personal operational state, not payroll reporting.

- `staff.clock_status` is the steady-state chip.
- `staff.clock_in_reminder` and `staff.clock_out_reminder` replace the steady chip when action is needed.
- `staff.hours_week_summary` can show own hours only.
- `staff.timesheet_approval_pending` and `staff.pay_period_ending` should focus on entries, corrections, and deadlines. They must not show pay amounts.

### Onboarding

Onboarding items should fade quickly as the staff member becomes operational.

- `staff.welcome_setup_steps` is the parent onboarding progress item.
- `staff.safety_protocol_ack` can be blocking and high urgency.
- `staff.onboarding_station_familiarization` links training to the actual station surface.
- `staff.team_introduction` is optional and should never interrupt active shift work.
- `staff.key_recipes_review` should be route-boosted on `/staff-recipes`.

### Personal

Personal items are allowed only when they help the staff member operate or stay compliant.

- `staff.training_opportunity` appears when assigned, recommended by chef, or relevant to upcoming station work.
- `staff.certification_expiring` is compliance-critical but still scoped to the staff member's own credential.
- `staff.performance_milestone` is celebratory and should never outrank live work.

## Scoring Assembly

Base scoring:

```ts
score =
  baseUrgency +
  pageAffinityBoostWhenRouteMatches +
  timeWindowBoost +
  unreadOrUnacknowledgedBoost +
  safetyBoost -
  suppressionPenalty -
  completedOrResolvedPenalty
```

Recommended boosts:

| Signal                                          | Boost                                   |
| ----------------------------------------------- | --------------------------------------- |
| Severe allergen or safety protocol active today | +25                                     |
| Staff is currently clocked in                   | +10 to current shift/station/task items |
| Due within 30 minutes                           | +20                                     |
| Due within 2 hours                              | +12                                     |
| Overdue                                         | +30, capped at 100                      |
| New chef-authored item                          | +15                                     |
| Item belongs to current station                 | +12                                     |
| Item belongs to today's event                   | +15                                     |
| Staff dismissed same item recently              | -30 until cooldown ends                 |
| Already acknowledged/read                       | -20 unless still actionable             |

Hard ordering overrides:

1. Severe dietary/allergen alerts.
2. Clock-out overrun and clock-in imminent reminders.
3. Overdue assigned tasks.
4. Same-day schedule/station changes.
5. Current station and station checklist.
6. Today's event timeline and special instructions.
7. Messages from chef.
8. Routine schedule, onboarding, and personal items.

## Suppression and Grouping Rules

| Rule                                          | Behavior                                                                                            |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Same task has multiple states                 | Show only the highest state: overdue > due soon > new > note > completed                            |
| Three or more active tasks for same context   | Use `staff.bulk_task_list` and place only safety/blocker task cards alongside it                    |
| Today's event has many cards                  | Show summary plus the highest two child alerts; keep the rest expandable                            |
| Station has checklist, equipment, and recipes | Show current station plus the most urgent child item                                                |
| Clock reminder active                         | Demote clock status and hours summary                                                               |
| Dietary alert matches recipe allergen flag    | Keep dietary alert primary; recipe allergen flag may appear on `/staff-recipes` or inside expansion |
| Schedule changed                              | Hide stale shift card and show new shift only after change acknowledgment                           |

## Privacy Contract

Staff rail data access must satisfy all of these checks before an item is emitted:

1. `requireStaff()` has authenticated the user.
2. Item tenant matches `user.tenantId`.
3. Item either targets `user.staffMemberId`, targets the staff member's assigned station/shift/event, or is explicitly shared to staff/team by the chef.
4. Item payload is reduced to operational fields before rendering.
5. Item expansion uses the same privacy filter as the collapsed rail item.

Forbidden fields in staff rail payloads:

| Domain             | Forbidden examples                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------- |
| Financials         | quoted price, payments, refunds, revenue, margin, food cost, labor cost, payroll amount, tips amount      |
| Client data        | phone, email, full address, payment profile, household details, private preferences, private notes        |
| Business data      | booking pipeline, lead value, conversion metrics, utilization, pricing strategy, market intelligence      |
| Staff-private data | other staff pay, disciplinary notes, private availability notes unless needed for a swap/coverage request |
| Vendor data        | invoice totals, contract pricing, vendor account numbers                                                  |

Allowed staff rail payloads:

| Domain    | Allowed examples                                                                      |
| --------- | ------------------------------------------------------------------------------------- |
| Schedule  | own shift time, assigned role, assigned station, coverage request                     |
| Event     | event type, guest count, service times, safe location note if chef-shared, menu theme |
| Safety    | allergen, severity, affected guest number, affected dish/station, prevention steps    |
| Task      | title, due time, priority, status, chef note, station, assigned recipe                |
| Recipe    | method, yield, ingredients, allergens, technique notes, chef-approved substitutions   |
| Inventory | item name, quantity, location, station impact, receiving instruction                  |
| Time      | own clock state, own hours, missing entry flags, approval state                       |

## Implementation Notes

- Prefer one compact rail item per operational concern. Staff should not have to read a feed.
- Every expandable item must be useful without navigation. Expansion should show the next action, not a second dashboard.
- Use route affinity aggressively: `/staff-time` should feel time-first, `/staff-station` should feel station-first, and `/staff-recipes` should feel prep-first.
- Use `quick_action` only where server actions can enforce staff ownership and tenant scoping.
- Do not let dismiss hide safety, overdue, active clock, or required acknowledgment items.
- Store impressions/dismissals by `{staffMemberId, itemId, sourceEntityId}` so one staff member's dismissal does not suppress another staff member's work.
- If a chef shares broad event notes, pre-process them into explicit staff-safe fields before rail assembly.
