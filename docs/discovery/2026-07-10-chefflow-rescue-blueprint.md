# ChefFlow V1 Rescue and Restructuring Blueprint (Final)

**Read-only discovery synthesis, assembled 2026-07-10. Merges the restructuring blueprint with five adversarial reviews (constraint verification, security, working-chef persona, language and naming, missing expectations). Nothing in this document deletes work. Every route keeps resolving.**

This is the deliverable requested by `docs/chef-navigation-decision-contract.md` Section 13 (:363). It extends, and where stated formally amends, that contract, `docs/specs/universal-interface-philosophy.md`, `docs/specs/navigation-action-bar.md` Principle 8 (:186, the directory is sacred), and the `tier` field already declared at `components/navigation/nav-config.tsx:107,136`. Every mechanism below extends something that already exists in the repo.

**Thesis.** The tension: the blueprint pillars claim 92 to 100 percent complete, the chef portal carries 731 pages across 100 sections, and the owner no longer runs his business in his own product. The two thinnest data domains (inquiries, recipes) are his two loudest unmet needs, while roughly 550 of 930 tables orbit peripheral systems. The app is bloated and incomplete at the same time. This document resolves that with tiering, not deletion: a 12-door floor any solo chef can run a booking on, named optional modules for everything else, an experiments shelf for the rest, and a written record of where every completeness claim was false. The floor already exists in code; the work is promotion, containment, and finishing roughly ten specific gaps, plus two security fixes without which the whole module system is decoration.

## 3. The true core product

ChefFlow's real product is a solo private chef's booking-to-payment loop: someone asks about a dinner, you answer fast, you quote it at a price that covers your food cost, you book it, you plan the menu, you know what to prep and what to buy, you cook the dinner with the allergies and the address in your pocket, you get paid, and you follow up so they book again. All of that exists in code today and it is the best-built part of the app. The free tier already agrees this is the product: `lib/feature-gates/gate-registry.ts:20-24` defines free as inquiries, events, clients, quotes, payments, calendar, basic finance, recipes, documents. The Core is the free tier promoted to the default experience.

## 4. The tier model

- **Tier 0, Core.** The floor. Visible on day 1 to every chef. Twelve doors. Never gated.
- **Tier 1, Standard.** On by default, one level below the floor: tabs of core surfaces or entries inside the core sidebar groups. Never competes with the floor for attention. No unlabeled catch-all group; every Tier 1 surface gets a named home (Records, Library, Setup) or a tab on a Tier 0 door. "Tools" as a junk-drawer label is banned.
- **Tier 2, Named modules.** Off the daily surface, turned on from `/settings/modules` (page exists: `app/(chef)/settings/modules/page.tsx`; precedent: Cannabis, Commerce, Locations already module-tagged per `docs/chef-portal-navigation-audit.md` Section 9 and nav-config.tsx:411,911). Full power preserved and reachable, deliberately chosen.
- **Tier 3, Labs.** Behind an experimental flag. Real code with zero users, admin-only tooling, or in-flight work. Labeled as experimental inside the app. Labs entries do not appear in the default module gallery; they are visible only once the experimental flag itself is on.
- **Tier 4, Shells.** The route stays alive as a redirect so links and habits never break. For routes that are already bare redirects, nothing changes. For live full pages being converted, the page's components are preserved as live files in the tree (moved into the target surface as a tab or view, or parked unrouted in the same directory); only the route file becomes a redirect, each conversion is recorded in `docs/CLAUDE-DOMAINS.md`, and each cluster gets owner approval first. "Preserved in git history" is not preservation under this project's own doctrine (`memory/feedback_never_delete_code.md`; the 279-file incident is the precedent).

**Enforcement mechanism (real files, in dependency order):**

1. **Server-side gating first, or none of this means anything.** `lib/billing/require-pro.ts:5-7` currently ignores its feature slug and returns `requireChef()`; 41 pages that believe they are behind a billing gate are not. `lib/feature-gates/gate-check.ts` exports `requireGate`, `checkGate`, `isGateEnabled` with zero consumers anywhere in `app/`, and `resolveChefTier` (:42-45) returns hardcoded 'free'. Fix: `requirePro` calls `requireGate`, the slug maps to a `GateKey`, and server components rendering gated content call `checkGate`. This lands before any nav retagging. A tier system that only hides links is client-side decoration; a chef who types a URL gets the feature regardless.
2. **Two axes, kept distinct.** Module on/off is a preference, stored where the settings page already writes it: the `enabled_modules` store behind `lib/billing/module-actions.ts:23-29` and `lib/billing/modules.ts`. Plan gating is billing, owned by `lib/feature-gates/gate-registry.ts` and the flags table `gate-check.ts:22` reads. A module can be ON while individual pro gates inside it stay locked. A one-page mapping table (blueprint module name, billing slug, gate keys, plan tier) is written before any dispatch, because today three vocabularies exist (`lib/billing/modules` 15 slugs, `lib/billing/focus-mode` CORE/EXTENDED, the gate registry) and the settings page consumes a different one than the draft assumed (`app/(chef)/settings/modules/modules-client.tsx:11-13`).
3. **The nav renderer reads the tier field.** `components/navigation/nav-config.tsx`: every entry tagged with `tier` and `module` (today 8 or 9 of roughly 600 are tagged). `components/navigation/chef-nav.tsx`: reads `tier` and the module map (today it reads neither the tier field nor per-tenant module state; :18-19 import navGroups, standaloneBottom, and only the static DEFAULT_ENABLED_MODULES). `components/navigation/action-bar.tsx`: capped by `MAX_PRIMARY_NAV_ITEMS` (`lib/interface/surface-governance.ts:1`, value 7, currently bypassed by the 13-item actionBarItems). **`components/navigation/chef-mobile-nav.tsx` is in the same write-set** (it independently imports navGroups and actionBarItems at :11-14 and hardcodes a `/tables` bottom tab at :280,319-322 that must route through the Labs flag). Desktop and phone ship the same items and labels in the same wave, asserted in the journey test.
4. **A rollback switch, not a revert.** One flag (`nav_tiered_ia`) added to the gate registry, default on; when off, chef-nav and chef-mobile-nav render the old ungated tree. The tier tags stay in the config either way, so backing out is a toggle and no tagging work is lost.
5. **Direct URLs never break.** A Tier 2 route visited while its module is off renders normally with a one-line, per-module header note that names the job ("This page belongs to Ticketed Dinners; turn it on in Settings"), phrased per module, shown only while off. Tier 4 shells use `redirect()` (a temporary redirect, matching the in-repo precedent at `app/(chef)/payments/page.tsx:7`), never a permanent one, because two shells are planned to be repointed and permanent redirects get cached by browsers forever. Module OFF means, precisely: removed from nav, from search promotion, from Today panels, and from cron and notification output; pages still resolve. The gallery card says so, so the toggle never overpromises.
6. **One route-alias map.** The redirect-shell conversion ships a shared old-path-to-canonical map, and every pathname-keyed system resolves through it: Rail `pageAffinity` (`lib/discovery/registries/chef-rail-registry.ts:2228-2330` keys recipe cards to `/culinary/recipes`), Remy starters (`lib/ai/remy-starters.ts:52` branches on `/expenses`), onboarding suggestions (`lib/onboarding/smart-suggestions.ts`), help sections (`lib/help/page-info-sections/07-...expenses...`, `12-...leads...`), and pinned/recent surfaces (`components/navigation/pinned-surfaces-section.tsx`, `recent-pages-section.tsx`, resolved on read, no data migration). Without this map, the app's own intelligence dies silently on every shell.
7. **Search stays whole.** `lib/search/universal-search.ts` keeps indexing the full config; tier affects promotion only.
8. **The measuring stick changes with the plan, in the same wave.** `scripts/regression-firewall.mjs:245-260` hard-fails on any weak or orphan route, `scripts/wiring-audit.mjs:410` defines WEAK by nav references, and the results file already carries one orphan (`/studio/preview`). The Phase A label sweep would remove exactly the nav references that keep marginal routes out of WEAK status, so the very first Phase A item teaches wiring-audit to read tier tags and assert reachability per tier (Tier 0/1 need nav refs; Tier 2 needs a gallery path; Tier 3/4 need a registry or redirect entry), plus an expected-orphan allowlist entry for `/studio/preview`. Otherwise every closeout gate goes red mid-restructure and agents start bypassing it.
9. **Hub subroutes obey modules too.** Module gating applies inside Tier 0 hubs; the worked example is Finance, where payroll, 941, W-2, and the tax center (nav-config.tsx:842-905) sit behind the Payroll and Tax module while payments, invoices, and the ledger stay on the floor. Every hub uses this same mechanism; no hub invents its own exception.
10. **The chef never sees tier vocabulary.** "Tier," "Standard," "Parked," "Archive" are internal words for this document and the config. The chef sees door names and module names only.
11. **Governing docs amended, not contradicted.** The contract amendment (filed before any tagging, because Tier 0 `/inquiries` conflicts with the locked "Pipeline is secondary" at contract :200 until amended in writing) records: Inquiries joins the floor and the word "Pipeline" is retired from the UI entirely; the money door is labeled Finance per contract :250 (David can veto at amendment review); `/settings/modules` is the single gallery and the regrouped directory must contain every one of the 474 existing links (the acceptance check that keeps Principle 8 satisfied); the Six Pillars remain the completeness ledger while the contract's domains remain the IA, stated explicitly because agents have treated the two as interchangeable and the Pillars have no home for Inbox at all.

These override anything else in this document. The first two are prerequisites for the module system; a chef who bookmarks or types a URL must meet server-side enforcement, not a missing nav link.

**Phase A, ride the nav sweep:** 3. **Four chef routes missing from middleware policy.** `/series`, `/business`, `/reference`, `/shopping-list` are absent from CHEF_PROTECTED_PATHS (`lib/auth/route-policy.ts:4-125`), so middleware classifies them public (fallback at :394). For authenticated users the :284 recheck skips role policy entirely on these. **Independent of the restructure, queued now:** 5. **E2E auth endpoint removed its production guard on purpose** (`app/api/e2e/auth/route.ts:25-26`); gates are two env vars plus a loopback check, and `.env.local:100` carries `E2E_ALLOW_TEST_AUTH=true`, which overrides `.env` if present on the production host.
